# Phase 1 Domain Model

## Scope and precedence

The Phase 1 brief approved by Nicolas supersedes the Phase 0 prohibition on
implementation. Organization is the only tenant boundary. No branches, customer
accounts, ERP, payments, GPS, offline sync or native apps are introduced.

This design is the pre-SQL checkpoint. Implementation is authorized by the brief;
commercial defaults and legal retention still require owner review. A source
implementation is not evidence of a successful Supabase deployment.

## Entities and ownership

| Entity              | Responsibility and lifecycle                                                                                                                                                                                          |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| auth.users          | Supabase-managed credentials, verified email, sessions and MFA. Never copy password hashes.                                                                                                                           |
| profiles            | One minimal display name per Auth identity; no organization column. Created by a small Auth insert trigger. Historical identity references use RESTRICT.                                                              |
| organizations       | Tenant name and active/suspended status. No deletion interface.                                                                                                                                                       |
| memberships         | Many-to-many profile/organization identity, OWNER/ADMIN/SUPERVISOR/TECHNICIAN, invited/active/suspended/removed state. Supervisor is a membership in the same tenant. Invitations may have no profile until accepted. |
| plans               | SOLO/NEGOCIO/EQUIPO/EMPRESA catalogue, without prices. Feature flags are bounded JSON configuration, not new speculative tables.                                                                                      |
| subscriptions       | One current entitlement per organization: plan, seat limit, status, validity and bounded feature overrides. No payment history.                                                                                       |
| clients             | Tenant-owned customer contact, address and notes; archived_at instead of hard deletion. No identity document, birth date or sensitive attributes.                                                                     |
| services            | Tenant-owned job, client, type, schedule, lifecycle, creator and timestamps. Cancellation preserves history.                                                                                                          |
| service_assignments | Current technician plus ended assignments. One current assignment per service; a reassignment never overwrites history.                                                                                               |
| reports             | Versioned service reports; draft/finalized, work/findings/recommendations, generated_at and snapshot. Finalized versions are immutable. No PDF engine.                                                                |
| evidence            | Private future storage object metadata attached to a draft report; no binary data or permanent public URL.                                                                                                            |
| signatures          | Receipt/acknowledgement metadata attached to a draft report. This does not assert satisfaction or legal acceptance.                                                                                                   |
| audit_events        | Append-only actor/entity/action/time metadata, without passwords, tokens, contact information or report bodies.                                                                                                       |
| platform_admins     | Explicit operator allowlist, separate from tenant memberships. No automatic access to operational contents.                                                                                                           |

## Invariants

- UUID keys generated by PostgreSQL; timestamptz for all operational timestamps.
- Composite foreign keys include organization_id for every tenant-to-tenant link.
- Exactly one active OWNER is created atomically with the tenant and subscription.
  Owner removal/demotion and ownership transfer are not exposed in this phase.
- Active memberships consume seats; invited/suspended/removed do not. Acceptance
  can fail when full. Membership changes lock the organization and check the
  subscription, preventing two activations from independently claiming one seat.
- Initial onboarding uses SOLO, one seat and a 14-day trial. This is an explicit,
  provisional lab default, not approved pricing or a commercial commitment.
- trial/active with a future valid_until (or active without an end) allow operations.
  Expiration and suspended/expired subscriptions deny operational reads and writes.
  Own membership and organization/subscription metadata remain available to explain
  access state. No data is deleted on suspension or expiry.
- Invitations last seven days, are bound to a verified Auth email, and require an
  authenticated acceptance. No application bearer invitation token is introduced.
  Email delivery remains an environment integration until SMTP is configured.
- All application DML uses narrowly authorized RPCs. Authenticated direct table
  writes are denied. RLS separately filters reads, including direct Data API calls.
- OWNER/ADMIN/platform administration require Supabase aal2. Bootstrap and own
  identity reads permit MFA enrollment; they do not permit operational access.
- Supervisors manage services they created or whose current technician they
  supervise. Technicians access only currently assigned services and associated
  clients/reports. Organization administrators operate throughout their tenant.

## Privacy and retention

Organization owns client contact and operational data. Profile display names are
owned by the individual. Invitations retain only the recipient email until accepted
or revoked; acceptance clears that address. Reports retain author membership IDs.
No automatic purge is implemented until the retention matrix is approved. This is
a production release gate, not permission to retain personal data indefinitely.

Storage uploads, PDF generation, support impersonation and session/device quotas
remain outside this implementation. See STORAGE.md and PENDING_DECISIONS.md.
